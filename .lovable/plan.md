# النشر على دومينك + خطة نسخ احتياطي/خروج إلى Supabase خاص بك

## الخلاصة (لماذا هذا الاختيار)

- Hostinger Business استضافة مشتركة PHP + MySQL. تطبيقك يعمل بـ TanStack Start على بيئة Node/Edge وقاعدته PostgreSQL — لا يمكن تشغيله هناك، ولا استيراد نسخة Postgres في MySQL.
- إعادة بناء المشروع من الصفر أو نقله عبر GitHub لن تغيّر شيئًا في مشكلة الاستضافة، وستكلّفك فقدان البيانات وسياسات الأمان (RLS) المضبوطة حاليًا على 17 جدولًا و5 دوال أمان.
- لذلك: نبقى على Lovable Cloud، ننشر من Lovable، ونستخدم Hostinger فقط كمزوّد للنطاق. ثم نجهّز مسار خروج آمن حتى لا تكون مقيّدًا مستقبلًا.

## 1) النشر وربط السَبدومين

- نشر التطبيق من Lovable (زر Publish).
- إضافة الدومين `projects.smartsociety.ee` في إعدادات النشر.
- في Hostinger: لوحة الدومين، ثم إعدادات النطاق، وإضافة سجل CNAME للسَبدومين يشير إلى القيمة التي تعطيها Lovable. الموقع الرئيسي `smartsociety.ee` يبقى عند Hostinger كما هو دون أي تغيير.
- بعد انتشار الإعدادات (عادة دقائق إلى ساعات) تُصدر الشهادة تلقائيًا ويعمل HTTPS.

## 2) بريد الدخول (Magic Link)

- الدخول الحالي بلا كلمة مرور عبر رابط بريدي. قبل الإطلاق للشركاء نضبط نطاق مرسل موثوق حتى لا تذهب الرسائل إلى Spam، ونجعل رابط العودة يستخدم الدومين النهائي بدل رابط المعاينة.

## 3) نسخ احتياطي دوري (ملف SQL)

- تصدير قاعدة البيانات من Lovable Cloud ينتج ملف SQL كامل (المخطط + البيانات + الدوال + السياسات).
- خطوات الاستعادة عند الحاجة، في أي Postgres (بما فيه Supabase الخاص بك):
  1. إنشاء مشروع Postgres/Supabase جديد.
  2. تشغيل الملف عبر `psql "<connection-string>" -f export.sql`
  3. إعادة إنشاء مساحة التخزين `project-documents` (خاصة) ونسخ الملفات إليها.
  4. مستخدمو المصادقة يُنقلون بشكل منفصل عبر أدوات Supabase، وليس ضمن ملف الـ SQL.
- نحتفظ داخل المستودع بملفات `supabase/migrations/` كمرجع للمخطط، بحيث يمكن إعادة بناء البنية في أي وقت حتى بدون البيانات.

## 4) مسار الخروج الكامل (متى تحتاجه فقط)

إذا قررت لاحقًا الاستقلال بالكامل عن Lovable Cloud:

1. مشروع Lovable جديد فارغ + ربطه بـ GitHub، ونقل الكود إليه.
2. ربط Supabase الخارجي الخاص بك في ذلك المشروع الجديد.
3. تشغيل ملفات الـ migrations لبناء نفس المخطط والسياسات.
4. استيراد ملف الـ SQL للبيانات، ثم نقل ملفات التخزين والمستخدمين.
5. النشر إلى Vercel/Netlify/Cloudflare (وليس استضافة Hostinger المشتركة)، وتوجيه نفس السَبدومين إليه.

هذا المسار ممكن في أي وقت لأن المخطط والكود قابلان للنقل — لكنه غير ضروري الآن.

## ملاحظات تقنية

- التطبيق: TanStack Start + React 19 + Vite، مع server functions — يتطلب بيئة Node/Edge.
- القاعدة: PostgreSQL مع RLS مفعّلة على كل الجداول ودوال security definer (`has_role`, `is_project_member`, `can_manage_project`, `can_contribute`, `shares_project_with_org`).
- التخزين: مساحة خاصة `project-documents` مع روابط موقّعة محدودة الزمن.
- الأسرار الحسّاسة (مفتاح الخدمة، مفتاح الذكاء الاصطناعي) تبقى على الخادم فقط.
